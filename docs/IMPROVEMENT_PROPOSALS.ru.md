# Fiximizer — предложения по улучшению и план интеграции

**Статус:** проектные предложения; это изменение затрагивает только документацию.  
**База аудита:** `main`, commit `9728fede8faf6ef6d34f1c4a87d1ecba3c5d9d19` (9 ноября 2026 года).  
**Целевая основа:** Minecraft 1.21.1, NeoForge 21.1.x, Java 21.  
**Область документа:** подготовка независимо проверяемых задач для будущей реализации и интеграции. Этот документ не объединяет, не перебазирует и не изменяет существующие feature-ветки.

## 1. Краткий итог

У Fiximizer уже есть полезная диагностическая основа: ограниченные runtime-измерения, запись и анализ JFR, отчёты об инцидентах, watchdog зависаний, необязательная телеметрия модов, контроллер давления на память и адаптивный планировщик собственных задач Fiximizer.

Следующий шаг — усилить цепочку **симптом → доказательства → диагностика → воспроизводимый тест → совместимое действие**. Предлагаются следующие дополнения:

1. **Diagnostic Bundle** — предсказуемый локальный архив для отладки и анализа ИИ с проверкой приватности перед экспортом.
2. **Benchmark Engine** — повторяемые сценарии и версионируемые baseline вместо разовых лучших результатов.
3. **Runtime Health Check** — понятное состояние и доступные возможности каждой подсистемы, включая причины fallback.
4. **Дальнейшее развитие Memory** — поиск крупных удерживаемых неизменяемых структур вместо массового переписывания объектов.
5. **Дальнейшее развитие Network Telemetry** — разделение наблюдений сырых буферов, серверной оценки задержки и локальных задержек обработки.
6. **Compatibility Capability Registry** — проверки версий и возможностей и отдельные решения о конфликтах для каждой функции вместо одной проверки mod ID.

Существующие реализации Startup, Memory и Network остаются в своих ветках. Их нужно отдельно проверить и подготовить к интеграции с актуальным `main`.

### 2.1 Ветка Startup

В отдельной ветке Startup уже есть первая реализация и техническое описание. Она записывает этапы Fiximizer, откладывает необязательную работу до стабилизации клиента и формирует небольшой локальный отчёт о запуске.

Важное различие измерений уже отражено в документации этой ветки: **от старта JVM до первого главного меню** включает JVM, Minecraft, NeoForge, все моды, ресурсы, файловую систему и запуск на конкретном компьютере. Это нельзя приписывать самому Fiximizer или отдельному моду.

Отдельно должны отображаться длительности этапов, принадлежащих Fiximizer.

Следующий шаг — проверка и подготовка этой реализации к интеграции, а не создание второго конкурирующего Startup Profiler.

### 2.2 Ветка Memory

В ветке Memory есть ограниченная таблица слабых ссылок для строк и обнаружение возможностей JVM. Текущая дедупликация строк намеренно узкая и сама по себе не доказывает экономию памяти на уровне всей сборки. Пользу конкретного адаптера нужно оценивать по реальным попаданиям и измерениям удерживаемой памяти.

Следующая полезная работа — профилирование крупных удерживаемых структур реальных сборок, после чего нужно отдельно изучать только кандидатов с явными гарантиями неизменяемости и владения данными. Технические заметки FerriteCore подходят для архитектурного исследования, но не для копирования исходного кода: [технические заметки FerriteCore](https://github.com/malte0811/FerriteCore/blob/0cef1f2add1f1329aa6e690e8e292acd625c5c6d/summary.md).

Ветка Memory также обнаруживает поддержку Compact Object Headers на тех runtime, где соответствующая VM-опция действительно существует. Это должно оставаться рекомендацией, основанной на проверке возможностей JVM: нельзя определять поддержку только по номеру Java и нельзя предполагать, что Java 21 предоставляет опцию из Java 25.

### 2.3 Ветка Network

Ветка Network сейчас представляет собой **пассивную телеметрию и эксперимент с узкой настройкой сокета**, а не замену транспорта Minecraft или ускоритель обработки пакетов.

Согласно документации ветки, реализация наблюдает байты/кадры сырых Netty `ByteBuf`, считывает сообщаемую Minecraft задержку игрока, имеет необязательную политику TCP_NODELAY и предлагает Java/Rust-реализации локального расчёта перцентилей.

Названия метрик должны точно отражать их смысл:

- `inboundFrames` / `outboundFrames` считают наблюдения сырых `ByteBuf`; их нельзя показывать как гарантированное количество пакетов протокола Minecraft.
- `PlayerInfo#getLatency()` — значение задержки, сообщаемое Minecraft для локального игрока. Это не независимое измерение ICMP/UDP RTT, потерь пакетов или серверного тика.
- Клиентский мод не может убрать физическую задержку маршрута в интернете или время обработки на удалённом сервере.

Rust backend только рассчитывает статистику для ограниченного локального массива измерений. Реальная выборка небольшая, поэтому при выборе Java/Rust нужно учитывать полную стоимость JNA/FFI-вызова, подготовки и копирования данных, прогрева и работы runtime. Java должна оставаться надёжной базовой реализацией, а Rust следует выбирать только после воспроизводимого сквозного выигрыша на характерной нагрузке. По документации ветки нативные артефакты упаковываются для Windows x86_64 и Linux x86_64; поддержку macOS нельзя заявлять, пока CI не собирает, не упаковывает и не тестирует соответствующую библиотеку.

## 3. Diagnostic Bundle

### Цель

Создать один предсказуемый архив, который поможет разработчику или ИИ разобраться в проблеме без ручного сбора несвязанных логов и скриншотов.

### Предлагаемое содержимое

Версионируемый архив может включать:

- `manifest.json` — версия схемы архива, версии Fiximizer, Minecraft, NeoForge и Java, операционная система и состояния функций.
- `system.json` — доступные процессоры, объём физической памяти, лимиты heap JVM, названия GC и доступные аппаратные возможности.
- `mods.json` — ID и версии модов только при явном включении списка модов пользователем.
- `performance.json` — сводки frame/client tick/server tick, давление на память, телеметрия очередей и выбранный профиль.
- `jfr-analysis.txt` — сводка анализа записи, выбранной пользователем или явно разрешённой для экспорта.
- `incident.json` — временная шкала соответствующего инцидента, сводка потоков и корреляционные данные, если они доступны.
- `network.json` — агрегированные счётчики и определения метрик; без сырых сетевых данных.
- `errors.log` — ограниченная по времени и количеству строк выборка релевантных ошибок.

Экспортёр должен включать только разделы, относящиеся к выбранной категории диагностики. Например, отчёт о рендеринге не должен автоматически включать сетевые данные или полный список модов.

### Приватность и обработка данных

- Создавать архив локально. Сетевая отправка не входит в эту функцию.
- Перед созданием показывать пользователю предварительный список файлов и категорий.
- По умолчанию исключать чат, содержимое пакетов, данные аутентификации, токены сессий, UUID, имена игроков, адреса серверов и полные локальные пути.
- Сначала применять структурированную очистку данных, затем текстовую санитизацию; несколько регулярных выражений не должны быть единственной границей приватности.
- Включение списка модов должно быть явным, поскольку он может раскрывать состав закрытой сборки.
- Ограничить размер отчёта, количество строк логов, JFR-экспортов и хранимых архивов.
- Использовать стабильные документированные JSON-поля, чтобы инструменты могли сравнивать отчёты разных версий.
- Записывать в manifest количество удалённых данных и исключённых разделов, но не сами удалённые значения.

### Критерии приёмки

1. Написать unit-тесты очистки на примерах путей, IPv4/IPv6, доменных имён, UUID, токенов, фрагментов чата и некорректных строк логов.
2. Проверять, что после очистки архив не содержит запрещённых исходных значений.
3. Проверять лимиты размера и количества файлов, обработку путей и совпадающих имён.
4. Убедиться, что отключённая диагностика и отсутствие JFR-файлов приводят к корректному частичному архиву, а не блокируют экспорт.
5. Проверить, что сжатие и файловые операции не выполняются в render, client-tick, server-tick или Netty event-loop потоках.

## 4. Benchmark Engine

### Цель

Заменить отдельные ручные замеры сопоставимыми измерениями до и после изменений. Результат бенчмарка должен описывать тестовую нагрузку, а не обещать универсальное увеличение FPS.

### Базовая архитектура

Каждый запуск бенчмарка должен иметь версионируемый manifest:

- ID бенчмарка и версия схемы;
- версии Minecraft, NeoForge, Java и Fiximizer;
- сводка аппаратных возможностей;
- отпечаток активных модов и конфигурации без приватных путей и идентификаторов;
- выбранный пользователем мир или сценарий;
- дистанция рендера, дистанция симуляции и важные графические настройки;
- длительность прогрева, измерения, интервал выборки и количество повторов;
- включённые функции Fiximizer и обнаруженные пересекающиеся оптимизаторы.

Результат должен содержать распределения и сводки, а не только одно число:

- p50, p95 и p99 времени кадра/render-call;
- p50, p95 и p99 client tick и integrated-server tick;
- MSPT/TPS там, где есть корректное измерение на стороне сервера;
- сводки CPU/allocation из JFR и паузы GC, когда запись включена;
- used/committed/max heap, память процесса и доступные измерения native/off-heap;
- ожидание очереди scheduler, время исполнения и счётчики отказов;
- GPU-метрики только тогда, когда драйвер или поставщик данных предоставляет достоверные значения.

### Модель сценариев

Начать с повторяемых сценариев, которые выбирает пользователь, а не с автоматизации игрового процесса:

1. **Простой в меню** — измерение накладных расходов мониторинга без загруженного мира.
2. **Стабильная сцена** — фиксированная позиция игрока, камера, время и количество сущностей.
3. **Сцена с большим количеством сущностей** — документированное количество и типы сущностей.
4. **Перемещение по чанкам** — повторяемый маршрут или подготовленная область мира.
5. **Перезагрузка ресурсов** — запуск пользователем с фиксированным набором resource pack.
6. **Нагрузка интегрированного сервера** — контролируемая сцена одиночной игры с документированной нагрузкой на тики.

Для baseline и нового варианта необходимо использовать одну и ту же сборку, мир, маршрут, прогрев и настройки. Сравнивать медианы и хвостовые перцентили нескольких запусков; холодные старты отделять от тёплых.

### Результат и критерии приёмки

- Хранить baseline локально в версионируемом формате.
- Разрешить явный импорт и экспорт файлов бенчмарков.
- Показывать baseline, новый результат, абсолютную и относительную разницу, количество выборок и разброс.
- Помечать сравнения недействительными, если существенно различаются версии, настройки или отпечатки сценариев.
- Учитывать накладные расходы самого Fiximizer.
- Добавить детерминированные unit-тесты агрегации, расчёта перцентилей, отсутствующих выборок и некорректных manifest.
- Не называть изменение оптимизацией, пока повторные тесты не покажут полезный сквозной выигрыш без регрессий корректности и совместимости.

## 5. Runtime Health Check

### Цель

Сделать понятным, какие подсистемы Fiximizer работают, какие намеренно отключены, какие не поддерживаются текущим runtime и какие завершились ошибкой.

### Предлагаемая модель состояний

Каждая подсистема должна предоставлять небольшую неизменяемую сводку:

- `HEALTHY` — инициализирована и работает.
- `DISABLED` — отключена конфигурацией или выбранным профилем.
- `DEGRADED` — основная функция работает, но необязательная возможность отсутствует.
- `UNSUPPORTED` — текущая ОС, архитектура, JVM или загрузчик не предоставляют нужную возможность.
- `FAILED` — инициализация или runtime-операция завершилась ошибкой; указать очищенную причину и состояние fallback.
- `NOT_STARTED` — отложенная инициализация ещё не запрашивалась.

Нужно показывать Startup, JFR, Diagnostics, Memory Guard, Scheduler, Memory Optimizer, Network Telemetry, Java/Rust backend, GPU telemetry, OpenCL, VRAM cache и необязательные интеграции модов.

### Требования

- Сбор статусов должен быть дешёвым и не должен повторно проверять оборудование из render loop.
- Для каждого статуса показывать время последнего изменения, короткую причину, активный fallback и необходимость действий пользователя.
- Ошибка необязательной подсистемы не должна ломать остальные подсистемы.
- Недоступный датчик GPU нельзя отображать как нулевую загрузку.
- Разделять «не измерялось» и измеренный ноль.
- Передавать те же очищенные статусы в Diagnostic Bundle.

## 6. Дальнейшее развитие Memory Optimizer

1. Получить baseline удерживаемой памяти на одной сборке, мире, runtime Java, настройках heap и последовательности прогрева.
2. Приписывать крупные группы объектов Minecraft, отдельному моду или общей библиотеке только при наличии доказательств.
3. Отдельно исследовать структуры BlockState, повторяющиеся multipart predicate/model, неизменяемые resource identifiers, baked quad data и VoxelShape.
4. Для каждого кандидата документировать неизменяемость, владельца данных, момент создания и правила инвалидирования.
5. Сравнивать кандидата с существующими оптимизаторами, например FerriteCore; не дублировать преобразования и сохранять отдельные переключатели функций.
6. Измерять retained heap после сопоставимых GC-точек, скорость аллокаций, паузы GC, нагрузку CPU и перцентили frame/tick.
7. Оставлять оптимизацию необязательной, пока не появятся повторяемая чистая выгода и тесты изоляции мутаций.

Не считать одно высокое значение heap-used утечкой памяти. Не заявлять об экономии фиксированного количества мегабайт по счётчику попаданий слабой таблицы. Сами ссылки, слоты, хеширование и счётчики тоже имеют стоимость.

## 7. Дальнейшее развитие Network Optimizer

1. Переименовать и документировать счётчики сырых буферов, чтобы интерфейс не называл их количеством пакетов протокола.
2. Разделять сообщаемую сервером задержку, независимый RTT, event-loop delay, время обработки пакетов и задержку серверного тика.
3. Добавить окна byte-rate и buffer-rate на ограниченных примитивных счётчиках; глубокую выборку включать только по запросу.
4. Профилировать текущий pipeline перед добавлением обработчиков или mixin. Фиксировать положение handler и обнаруживать повторную установку.
5. Измерять полный путь Java и Rust: подготовку данных, стоимость native-вызова, копирование памяти и проверку результатов.
6. Оставить TCP_NODELAY выключенным по умолчанию и сохранить восстановление предыдущей настройки сокета; оценивать влияние только на контролируемых тестах с разными серверами и платформами.
7. Не включать изменения кодирования пакетов, сжатия, pooling, flush policy и протокола в первую стадию до появления точных тестов порядка/фрейминга и матрицы совместимости.
8. Сохранять Java fallback и обычный транспорт Minecraft при отсутствии нативных библиотек или необязательных интеграций.

## 8. Реестр возможностей совместимости

Следующий слой совместимости должен отделять **обнаружение** от **разрешения на оптимизацию**.

Каждый адаптер должен объявлять:

- альтернативные mod ID и поддерживаемый диапазон версий;
- конкретную возможность или hook, который ему нужен;
- сторону работы: клиент, сервер или обе;
- функции, с которыми он пересекается;
- статус тестирования для каждой поддерживаемой линии Minecraft/NeoForge;
- безопасный пассивный режим и причину отключения оптимизации.

Совместимость нужно решать отдельно для каждой функции. Обнаружение Krypton должно отключать только конфликтующие сетевые изменения, но не несвязанные диагностические функции. Обнаружение FerriteCore должно блокировать только повторные преобразования памяти, которые доказанно пересекаются с его работой. Неподдерживаемые версии должны возвращать понятный статус, а не запускать экспериментальные invasive hooks.

## 9. Условия интеграции и тестирования

Перед объединением любой независимой реализации с `main`:

1. Получить актуальный `main` и сравнить его с feature-веткой; не использовать старые значения ahead/behind.
2. Проверить полный diff и сохранить независимые изменения обеих линий разработки.
3. Разрешать конфликты явно; это предложение не выполняет force-update и не объединяет одну feature-ветку с другой.
4. Запустить unit-тесты Java 21 на Windows и Linux.
5. Запустить применимую матрицу сборки NeoForge и проверку ресурсов/переводов.
6. Запускать тесты Rust и нативной сборки только для платформ, для которых действительно упаковываются артефакты.
7. Проверить запуск клиента и dedicated/integrated server там, где это относится к функции.
8. Проверить включённый и выключенный режимы, отсутствие необязательных зависимостей, неподдерживаемые платформы и fallback.
9. Приложить бенчмарки и данные совместимости к будущему обзору интеграции.

Порядок объединения независимых линий выбирается после просмотра их актуальных diff. Этот документ не задаёт очередность merge и не разрешает объединять какие-либо ветки.

## 10. Предлагаемый порядок реализации

| Очерёдность | Задача | Причина |
|---:|---|---|
| 1 | Проверить и подготовить Startup Optimizer | В отдельной ветке уже есть узкая реализация и тесты |
| 2 | Diagnostic Bundle | Сделает отчёты об ошибках и ревью кода значительно полезнее |
| 3 | Runtime Health Check | Покажет fallback и сбои отдельных подсистем |
| 4 | Benchmark Engine | Создаст измерительную основу для последующих оптимизаций |
| 5 | Эксперимент с Memory-кандидатом | Только после профилирования retained heap |
| 6 | Уточнение Network Telemetry | Сначала исправить семантику метрик |
| 7 | Реестр возможностей совместимости | Объединит проверки конфликтов на уровне отдельных функций |

Это предложение по приоритетам, а не график релизов. Измеренная регрессия или проблема совместимости может изменить очерёдность.
